# IdeaHub 工程铁律（可执行版）

本 skill 是仓库根目录 [`AGENTS.md`](../../../AGENTS.md)（唯一正本）的展开版，
补充了事故细节与判断依据。两者冲突时**以 `AGENTS.md` 为准**。

**适用范围**：`ideahub-server`、`ideahub-client`、`ideahub-app`。
三者各自独立部署、通过 HTTP 契约耦合，**彼此不知道对方线上跑的是哪个版本**。

---

## ⛔ 本仓头号注意：push 到 `main` = 直接部署到生产

`.github/workflows/deploy.yml` 监听 `push: branches: [main]`，SSH 到 ECS 跑 `deploy.sh`，
**没有人工审批环节**。开分支 → 自测（`npm test` 全绿 + `npm run check:config` 通过）
→ 再合并。合并那一刻就是发布。

---

## 接手任何工作时

1. `git pull` 当前仓库（跨仓改动则三个都 pull），并向用户报告结果
2. 工作树里若有同事未提交的 WIP，忽略它，不主动处理
3. 再读文件、再改代码

**在下"仓库里没有某段代码"这个结论前先 pull。** grep 不到 ≠ 不存在，
很可能只是本地落后，代价是几秒钟，错了的代价是一份重复实现。

## 铁律速查

完整表述见 `AGENTS.md`。这里只列**判断依据**——规则显得繁琐时用它说服自己或用户。

| # | 铁律 | 判断依据 |
|---|---|---|
| 1 | 动手前先 pull | 会话摘要是历史快照，不是本地状态 |
| 2 | 不动同事 WIP | 不确定是谁的 → 就是别人的 |
| 3 | 密钥只进 `.env` | 带 `VITE_` 前缀 = 发给每个用户 |
| 4 | 只走发布链路 | 手改线上的东西下次部署就被覆盖，且不留记录 |
| 5 | 验证认证据 | "我改了所以应该好了" 不是证据 |
| 6 | 一条规则一处实现 | 规则变了是否必须同时改两处？是 → 合并 |
| 7 | 配置先验证再落盘 | 写坏了服务起不来，且是在重启那一刻才发现 |
| 8 | 失败要响且局部 | 静默降级的东西没人会去看 |
| 9 | push 前更新文档 | 文档与代码不同步比没文档更坏 |
| 10 | 注释写为什么 | "是什么" 代码本身已经说了 |

## 真实事故复盘

这些全部发生在本项目，不是理论洁癖。规则显得繁琐时读对应条目。

### 一、限流静默失效（对应铁律八）

`rateLimit` 中间件的兜底 `catch` 是 fail-open（出错就放行）。
`clientIp()` 在 `req.headers` 缺失时抛 `TypeError`，正好被这个 catch 接住 ——
于是**限流对所有请求静默失效**，而日志里什么都没有。

- 症状：无。这是最坏的一类缺陷。
- 发现方式：写测试时构造了一个没有 headers 的假 req。
- 修法：`clientIp` 全程可选链；兜底放行必须打日志。
- 教训：**兜底 catch 会把 bug 变成"功能正常但没生效"**。凡是 fail-open 的地方，
  都要问"如果它一直在 fail，我会知道吗？"

### 二、装 Redis 把 Redis 装挂了（对应铁律七）

安装脚本直接写 `redis.conf` 然后 `systemctl restart`。配置里用了
`bind 127.0.0.1 -::1` —— `-` 前缀是 Redis **6.2+** 语法，机器上是 6.0.16，
服务当场起不来。

- 我给 nginx 写脚本时用了 `nginx -t` 做落盘前校验，**给 Redis 写脚本时却跳过了等价步骤**，
  因为 Redis 没有现成的校验命令。
- 修法：用**临时端口试跑** `redis-server <候选配置> --port 63799` 代替语法检查，
  起得来才落盘。
- 教训：**"这个工具没有校验命令"不是跳过校验的理由，是自己造一个的理由。**

### 三、三次"验证假阴性"（对应铁律五）

同一天连续踩三次，形态都是"我测了，结论是没生效"，而实际上是**测法本身不成立**：

1. `systemctl reload nginx` 是**异步**的。reload 返回成功后立刻请求，
   命中的可能还是旧 worker。
2. 用 `/proc/<pid>/environ` 查进程环境变量，看不到 dotenv 在运行时注入的值 ——
   它只反映 exec 时的环境。
3. 非 root 跑 `nginx -T` 会在读不到某个文件时提前退出，
   于是 `nginx -T | grep -c xxx` 返回 0，看起来像"配置里没有"。

教训：**读数为"没生效"时，先排除测法问题，再下结论。**

### 四、单次测量的陷阱（对应铁律五）

改完部署脚本量了一次耗时 18.43s，比改之前慢很多，差点回滚。
连续量三次是 ~3.0s —— 那次 18s 是冷启动。

教训：**性能结论至少三次测量。**

### 五、管道吞掉测试失败（对应铁律五）

`npm test | grep "Tests:" && git commit` —— 退出码取自最后一个命令（grep），
测试失败照样提交。

教训：**要判成败就分开跑**，不要把断言塞进管道。

### 六、pm2 在错误的用户下起了第二份服务（对应铁律四）

用 root 跑了一次 `pm2 reload ecosystem.config.js`。该命令在**进程不存在时会直接新建**，
于是起出一份与 deploy 用户平行的重复服务：两份同时监听、内存翻倍，
而且 deploy 用户的 `pm2 list` 里根本看不到它（pm2 的进程表按用户隔离）。

教训：**`pm2 reload <文件>` 不是纯粹的 reload，它兼具 start 语义。**
只用 deploy 用户操作 pm2。

### 七、部署脚本的兜底分支悄悄回退了架构（对应铁律六的精神）

`deploy.sh` 里 "进程不存在就拉起" 的兜底分支写的是
`pm2 start npm --name ideahub-server -- start` —— **fork 模式 + npm 入口**。
主路径已经改成 cluster + `ecosystem.config.js`，但兜底分支没跟着改。
一旦进程丢失（机器重启后 resurrect 失败等），部署会把它**悄无声息地重建成旧架构**：
cluster、多实例、零停机全部消失，**而且不报任何错**。

教训：**"回退到旧行为且不报错"的路径比直接失败更危险。**
同一个决策出现在主路径和兜底路径时，就是铁律六说的"两处实现"。

### 八、给一个不生效的配置文件写了半天（对应铁律五）

给 client 仓写了 `vercel.json` 配安全响应头。但生产环境是 **ECS 上的 nginx**，
根本不过 Vercel —— 那份配置从头到尾没有任何作用。

教训：**改配置前先确认"线上到底是谁在读这份配置"。**

### 九、新 worktree 里 AI 全是 mock（对应铁律三）

`.env.local` 被 gitignore，用 `/worktree` 开新工作区时不会跟过去。
新工作区里 `ARK_API_KEY` 为空 → `__AI_REAL__` 为 false → AI 静默走 mock。

教训：开新工作区第一件事是 `cp` 一份 `.env.local` 过去。

### 十、方舟的内容过滤是 400 不是降级（app 特有）

提示词里出现「少女」「拥抱」「害羞」等词，或要求**一张图里画多个角色**，
方舟会返回 400 `InputTextSensitiveContentDetected`，**整个请求失败**。

- 二分定位过：多角色同框这件事本身就被拒，换措辞绕不过去（试了 6 种）。
- 要多个姿势 → 逐张生成，靠传 `image` 参考图锁形象。
- 要中间动作帧 → 用 Seedance 首尾帧模式，不要找外部插值服务。

## 本项目特有的技术约束

### Express 5（server）

`req.query` 是**只读 getter**。任何试图给它赋值的中间件都会抛错 ——
`express-mongo-sanitize` v2 和把 `req.query` 整体替换的校验中间件都踩过。
需要清洗 query 时改成逐字段就地修改，或把清洗结果放到别的属性上。

### 限流按账号严、按 IP 松（server）

登录限流是**按账号 10 次/15 分钟（严）、按 IP 60 次/分钟（松）**。
不是笔误：CGNAT 环境下大量真实用户共用一个出口 IP，按 IP 卡严会误伤整片用户。

### 限流计数走 Redis 的 Lua 原子脚本（server）

`INCR` 和 `PEXPIRE` 必须在一个 Lua 脚本里做完。分成两条命令时，
若在两者之间崩溃，会留下一个**没有 TTL 的键 = 该账号被永久封禁**。

### AI worker 只在一个 cluster 实例上跑（server）

靠 `NODE_APP_INSTANCE === "0"` 判断。新增任何常驻任务都要显式判断，
不要指望"它在别的实例上自然跑不起来"。

### nginx 的 `add_header` 不会继承（server/client）

子 location 里只要出现**任何一条** `add_header`，父级的全部失效。
加安全响应头时要么全放在同一层，要么每个子 location 都补齐。

### 数据字段迁移（app）

本地库（IndexedDB）新增字段时必须同时写迁移。可选字段读不到不会报错，
老设备上就是静默显示 0/空 —— 只能靠迁移补。
